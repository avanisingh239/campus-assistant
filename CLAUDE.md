# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

This is a Next.js 15 (App Router, TypeScript) + Supabase + Google Gemini project. The scaffold, auth/role routing skeleton, one real end-to-end ingestion pipeline (paste text → Gemini extraction → validated data → database rows), the clash/free-slot deterministic engine, five real student screens — the **Student Dashboard (Action Plan tab)**, the **"Don't Miss This" discovery feed**, the **Communities directory**, the **Timetable**, and the **Ingestion page** — one real admin screen, the **Admin Dashboard**, and the real, branded **public landing page** (`/`), all exist and are wired up — see §Student Dashboard, §"Don't Miss This", §Communities directory, §Timetable, §Ingestion page, §Admin Dashboard, and §Public landing page below for those specifically. **Every other page is still a one-line placeholder.** `app/admin/submit/class`, `app/admin/submit/society`, and `app/admin/history` no longer exist at all — they started out as exactly that kind of placeholder once their functionality was folded into `/admin/dashboard` instead (see §Admin Dashboard for why), then were deleted outright, along with their admin-nav links, once nothing pointed at them anymore. That's still true of any *other*, not-yet-touched admin screen: that UI is being designed separately, one screen at a time, and will replace its placeholder as those prompts arrive. Don't build real UI into those *other* routes without being asked; do wire up data/logic that a future UI will need — same as `lib/engagement/actions.ts` already did for the clash engine (`lib/timetable/actions.ts` is the same idea, now with a real caller — see §Timetable), and the dashboard's Server Actions now do for engagement.

**AI provider note:** this project has used the Claude API, then Gemini, in the space of a few commits — that's not churn to "fix," it's a deliberate cost call. The extraction layer runs on **Google Gemini's free tier** (`gemini-3.6-flash`, `lib/ai/gemini.ts`) specifically because this is a hackathon project with no billing account attached: Gemini's free tier needs no credit card, where the Claude API does. The Zod-validation architecture is provider-agnostic by design (see below) precisely so this kind of swap stays cheap. If budget opens up post-hackathon, switching back to Claude (or any other provider) means touching `lib/ai/gemini.ts` and `lib/ai/extract.ts` only — `lib/ai/extraction-schema.ts` and `lib/ingestion/ingest.ts` shouldn't need to change for a provider swap alone, and didn't for either of the last two.

**Model name churn:** the model string in `lib/ai/gemini.ts` has already had to change once (`gemini-2.5-flash` → `gemini-3.6-flash`, retired for new API keys) — Gemini's model lineup moves fast. If `/student/ingest` starts 404ing on the model name again, the fix is the same: the error message itself names the current replacement model; trust that over anything cached here.

Before writing feature code, read the docs below — they are the **authoritative, approved spec** for what to build, with one correction: **`supabase/schema.sql` is the single source of truth for the database schema**, not `docs/data-model.md`'s prose (that file is now a walkthrough of the real schema, kept in sync by hand — if they disagree, the SQL file wins). Where a doc marks something `Unresolved` or `Deferred but Committed`, treat it as explicitly out of scope until the user says otherwise.

## Core architectural rule: AI extracts, deterministic code decides

- **Gemini (`gemini-3.6-flash`, via `lib/ai/gemini.ts` / `lib/ai/extract.ts`) is only allowed to write**: `category`, `title`, `why_it_matters`, `what_to_do_next`, `confidence`, `confidence_note`, the extracted date/time fields, `linked_class_name`, `match_confidence`, `seat_count`/`seats_unclear`, and `link_url`. It never computes `urgency_score`, `consequence_weight`, or `priority_score` (a generated column), and it never decides `clashes`/`free_slots` rows or `link_verified` (see §Link verification below — that field was never part of the AI's contract at all, not something taken away from it).
- **Gemini's output is untrusted input**, validated twice: once explicitly in `lib/ai/extract.ts` (`JSON.parse()` + `ExtractionBatchSchema.safeParse()` — Gemini's own `responseJsonSchema` is only a best-effort hint, see `docs/ai-contracts.md` §4, so this app-level parse is the real gate, unlike the Claude API's `messages.parse()` which validated inline), and again by `lib/ingestion/map-to-announcement.ts`'s pure transform before the row is inserted.
- **Part of the deterministic engine is implemented**: clash detection (class-vs-class, class-vs-event, event-vs-event), free-slot matching, and link verification live in `lib/deterministic/` and `lib/ingestion/verify-link.ts` — see §Deterministic engine and §Link verification below. Deduplication ("Confirmed by N sources"), the priority formula, and the time-decay cron are still just comments/notes in `supabase/schema.sql` and `docs/data-model.md` §5. `lib/ingestion/ingest.ts` currently inserts a new `announcements` row per extracted item unconditionally — no dedup check yet.

## Link verification (lib/ingestion/verify-link.ts)

A real bug found in testing: a message containing `https://whatsap-group-join.xyz/abc123` (misspelled "whatsapp," a `.xyz` domain — a fairly obvious spoof) reached students with an effectively "verified" link. The root cause wasn't a bad AI call — **`link_verified` was never part of the AI's contract at all.** `ExtractedAnnouncementSchema` (`lib/ai/extraction-schema.ts`) never included it, `docs/ai-contracts.md` §3's own removed-fields list confirms this, and `toAnnouncementRow` never set it either — the column just sat at its DB default (`true`, `supabase/schema.sql`) for every announcement that has ever existed in this app. CLAUDE.md's own §Communities directory note used to (incorrectly) claim this was "already set by the extraction schema" — it never was; that claim has been corrected below and in the docs it pointed to.

- **`verifyLink(url, context)`** (pure, unit-tested, no network access — a domain-string check, not a live reachability/reputation lookup) is now the actual source of truth for `link_verified`, called from `toAnnouncementRow` (`lib/ingestion/map-to-announcement.ts`) with `context` set to the original raw message text (not the AI's paraphrased title — the point is to check what was actually written, staying deterministic end to end).
- **`TRUSTED_LINK_DOMAINS`** — an exact-hostname allowlist (after lowercasing and stripping a leading `www.`), not a suffix check: `chat.whatsapp.com`, `t.me` (Telegram — `docs/product-spec.md` Area A.3/§3 names it alongside WhatsApp for the same "Group Link Directory" feature), `forms.gle`, `docs.google.com`, `google.com`. Deliberately exact-match rather than `hostname.endsWith("google.com")`, which would also match a lookalike like `evil-google.com`. Anything not in this set defaults to unverified — per the task that added this file, a false "unverified" (a student double-checks a real link) is far cheaper than a false "verified" (a student trusts a scam link), so this list only grows for a genuinely common legitimate domain, never for "probably fine."
- **Context override, the exact bug case**: if the raw message text explicitly claims "WhatsApp group" (a literal, case-insensitive check for both words present — not an AI judgment) but the URL's hostname isn't `chat.whatsapp.com`, that overrides everything else and forces unverified, even if the domain would otherwise be on the allowlist (e.g. a message claiming to be a WhatsApp group link that actually points at `forms.gle`). This check is deliberately scoped to WhatsApp only, matching the task's literal ask — a symmetric Telegram version would be a cheap, natural follow-up but wasn't requested.
- **Wiring**: `toAnnouncementRow(item, rawMessageText)` gained a required second parameter for this — every call site (just `lib/ingestion/ingest.ts`, passing the already-in-scope `trimmed` raw text) had to be updated, along with `map-to-announcement.test.ts`'s existing calls.
- **`docs/product-spec.md`'s "Link Safety [Source 4.4]: URLs are regex-validated..."** is now real (domain-allowlist rather than a generic regex, which is the stronger, more literal fix for "is this a legitimate platform domain" than a regex could be) — its own "As built" note, and the matching ones in `docs/requirements-traceability.md` Feature 4.4 and this file's §Communities directory, have been corrected to stop claiming the AI ever set this field.

## The one working pipeline

`lib/ingestion/ingest.ts` (`ingestRawText`, a Server Action) is the real, tested path: raw pasted text → insert into `messages` (via the service-role client) → `lib/ai/extract.ts` calls Gemini → Zod-validated → one `announcements` + `announcement_sources` row per extracted item. It also returns a summary (`id`/`category`/`title`/`confidence`) for each extracted item, on top of the plain id list it always returned — added so the real ingestion page (see §Ingestion page below) can show a student what was extracted without a second round-trip fetch.

`lib/ai/extract.ts`'s system prompt is built per-request by `buildSystemPrompt(now)`, not a static string — it includes a `CONTEXT` block with the extraction request's current date so Gemini can resolve relative day/time references ("tomorrow", "Friday", "next Monday") into concrete `event_date`/`deadline_at` values. Before this, the model had no anchor date at all, so any relative-only reference correctly (per its own "never guess" rule) came back `null` — this silently affected every category that uses dates, not just deadlines, until fixed. See `docs/ai-contracts.md` §1/§4.2, kept in sync with the actual prompt.

Gemini's free tier is rate-limited to roughly 10 requests/minute — `extractAnnouncements()` retries a 429/503 with backoff (1s, 2s) before throwing `RateLimitError`, which the ingestion page's Failed result state surfaces as a plain error message rather than a crash.

## Ingestion page (/student/ingest)

Real, authenticated, user-facing implementation of docs/product-spec.md Area A.4's Message Ingestion Drawer — promoted to its own tab/route the same way "Don't Miss This" was promoted from a dashboard lane (see §"Don't Miss This" above), rather than built as a slide-over drawer. This **replaces `app/(dev)/ingest-test`, which has been deleted** — that route was always meant to be temporary (see its own doc comment, now gone with it) and is fully superseded: same underlying pipeline, but a real UI wired to the signed-in student's session instead of anonymous/unauthenticated.

- **Nothing about the pipeline itself changed.** `lib/ingestion/ingest.ts`'s `ingestRawText` is called directly from the Client Component tree here exactly like it was from `/ingest-test`'s — same service-role write path, same Zod validation, same free-slot matching. The only new thing `ingestRawText` does is pass `submittedBy: user.id` (the signed-in student, from `page.tsx`'s `auth.getUser()`) as the `messages.submitted_by` value, and return the small per-item summary mentioned above.
- **One page, internal state** (same consolidation pattern as `/login` and `/student/timetable`): `choose` (source-select tiles) → `paste` or `upload` (the matching form) → `processing` (real loading state, not a frozen button) → `result` (one of 5 states).
  - **Choose source** (`source-select.tsx`): "Paste messages" and "Upload WhatsApp .txt" as real, tappable tiles; a third, visibly disabled "Share to app — Coming soon (Phase 2)" tile for Web Share Target, matching `docs/product-spec.md`'s own explicit Phase-2 tag for it (not built as functional, per that doc's own instruction).
  - **Bulk paste** (`paste-form.tsx`): a real styled textarea (not `/ingest-test`'s bare HTML default) plus the same "source group name" field that dev harness had.
  - **WhatsApp `.txt` upload** (`upload-form.tsx` + `lib/ingestion/whatsapp-parser.ts`): `parseWhatsAppExport` (pure, unit-tested, no DB access) splits one exported chat file into one raw-text payload per sender turn, by detecting WhatsApp's own `date, time - Name: message` line format — multi-line messages (no timestamp on continuation lines) stay attached to the turn they belong to, and timestamped lines with no `Name:` prefix (system notices like "Messages and calls are end-to-end encrypted...") are counted and dropped rather than becoming their own announcement. Returns `null` (not an empty list) when zero lines matched the timestamp pattern at all — that's what drives the Unsupported Format result state, distinct from "matched the format but every message was a system notice" (which returns an empty `messages` array and is a legitimate, if unusual, `successfully_parsed` run with nothing to show). Each resulting message is submitted with `source_type: 'whatsapp_export'` (already an existing `source_type` enum value in `supabase/schema.sql`, unused until now) through the exact same per-message call as a single paste — a batch is just N sequential calls to `ingestRawText`, capped at `MAX_BATCH_SIZE = 25` messages (see `ingest-screen.tsx`'s doc comment: Gemini's free-tier rate limit means one call per message, sequentially, would make a large export take minutes) with the result panel saying plainly when this truncated something.
  - **Processing**: a real spinner, with a live "Processing N of M…" progress bar once a batch has more than one message — not one opaque spinner for the whole batch.
  - **Result — 5 of the 9 states `docs/product-spec.md`'s Ingestion States list names** (see `lib/ingestion/result-state.ts`'s `classifyIngestOutcome`, pure and unit-tested, for the exact rules): `successfully_parsed`, `partially_parsed` (a `.txt` batch with some messages succeeding and some failing — both counts shown, nothing silently hidden), `needs_clarification` (every extracted item in the run came back `confidence: unclear` — still saved, just flagged as needing a closer look, rather than presented as a normal confident result; a single unclear item within an otherwise-fine batch is shown inline instead, same as the dashboard's own confidence badges), `unsupported_format` (the parser found no WhatsApp timestamp lines at all), and `failed` (a genuine `ingestRawText` error, e.g. `RateLimitError` — with a Retry button that re-runs the exact same batch, not a dead end). **`duplicate_input` is deliberately not built** — it needs the dedup engine `supabase/schema.sql`'s closing notes still describe as not existing (see this file's Core architectural rule section) — matching the task's own instruction to skip it rather than fake it.
- **`app/student/tab-row.tsx`** gained a 5th tab, "Add messages" (`ChatBubbleIcon` — the one background-decoration symbol from `components/canvas-background.tsx` that wasn't already reused as a tab icon; the other three each already were).
- **`lib/dashboard/category-meta.ts`** gained a shared `CONFIDENCE_LABELS` export (`✅ Clear` / `⚠️ Partially clear` / `❓ Unclear`), pulled out of `card.tsx`'s previously-local `CONFIDENCE_META` once the result panel needed the exact same three labels — same "extract on second use" pattern as `AppHeader`/`TabRow`/`fieldErrorsFromZod`.
- `app/(dev)/clash-test` still exists for testing the clash engine with an arbitrary pasted-in student UUID rather than a real session — its own doc comments no longer reference the deleted `/ingest-test`.
- **Every result state's secondary button resets back to the Choose Source screen without navigating to the dashboard first** (`onIngestMore` → `screen = "choose"`) — this has been true since the page's very first commit, for every one of the 4 built result states, not just the success ones; a later pass found the *labels* inconsistent (`"Add more messages"` for success/needs-clarification, but a plain `"Back"`/`"Try again"` for the other two, easy to misread as not offering this at all) and standardized all of them to `"Add another message"` so the capability reads the same regardless of which result state a run lands on. No new navigation logic was needed — this was a labeling fix, not a missing feature.

## WhatsApp webhook (app/api/whatsapp-webhook)

A third real caller of `lib/ingestion/ingest.ts`'s `ingestRawText`, alongside `/student/ingest` and (historically) `/ingest-test` — a Meta WhatsApp Cloud API webhook that feeds a live 1:1 WhatsApp forward into the exact same pipeline, no duplicated extraction/validation/write logic.

- **Not literally `docs/requirements-traceability.md` Feature 5.3** ("WhatsApp Business Bot," Admin Experience, **Stretch**, **Deferred but Committed**) — that feature is CR-scoped structured submission into an `admin_submissions` table that doesn't exist anywhere in `supabase/schema.sql` (every `/admin/submit/*` route is still a placeholder, so 5.3 as originally specified isn't buildable yet regardless). What's built here is narrower and unrelated to admin scoping: any inbound WhatsApp message, from anyone, routes through the same general/unauthenticated-paste-shaped pipeline `messages`/`announcements` already support — an extension of Area 1's ingestion surface (Bulk Paste, WhatsApp Export), not an implementation of 5.3. The explicit task that added this route asked for exactly this, which is why it wasn't treated as out of scope despite 5.3's tag — see this file's own repository-state paragraph ("treat as out of scope until the user says otherwise").
- **`GET` — Meta's webhook verification handshake**: echoes `hub.challenge` back with a 200 when `hub.mode=subscribe` and `hub.verify_token` matches the `WHATSAPP_VERIFY_TOKEN` env var, else 403.
- **`POST` — the actual message path**: `lib/ingestion/whatsapp-webhook.ts`'s `parseWhatsAppWebhookPayload` (pure, unit-tested, no DB access — same shape as `lib/ingestion/whatsapp-parser.ts`) extracts `{from, body}` pairs from Meta's `entry[].changes[].value.messages[]` payload via a lenient Zod schema, returning an empty array (never throwing) for anything that isn't a plain text message — a delivery-status callback, a read receipt, an image/audio/location message with no `text.body`. The route responds `200` immediately either way (Meta retries, creating duplicate processing, if a webhook response is slow), then hands any parsed messages to `next/server`'s `after()` — not a bare fire-and-forget promise, which could get frozen mid-flight the instant the response is sent on Vercel's serverless runtime; `after()` is the framework-provided primitive for exactly this "keep running after the response, guaranteed" case, and this project is already on Next 15.5, which has it stable (not `unstable_after`).
- **New `source_type` enum value, `whatsapp_bot`** — distinct from `whatsapp_export` (a bulk `.txt` chat-history upload via `/student/ingest`), since a live 1:1 forward is a different provenance worth being able to tell apart later. `sourceGroupName` is set to the sender's phone number (`message.from`) — there's no real group name for a 1:1 forward, and the trace-to-source drawer already has a graceful `?? "UNKNOWN SOURCE"` fallback pattern for missing group names, so this is at least real, present data rather than null.
  - **⚠️ Requires a schema migration that hasn't been applied to the live project yet** (same pattern as the `announcement_sources`/`contradictions` RLS-policy migration in §Student Dashboard above) — Postgres enums can't be altered by re-running `create type`, so run this directly against the live Supabase project:
    ```sql
    alter type source_type add value 'whatsapp_bot';
    ```
    Until this runs, any inbound webhook message will fail at the `messages` insert step with a Postgres enum-violation error (logged via the route's own `console.error`, not thrown back at Meta — Meta already got its 200).
- **Optional confirmation reply** (`lib/whatsapp/send-reply.ts`'s `sendWhatsAppReply`) — a plain `fetch()` call to the Cloud API's Send Message endpoint, using `WHATSAPP_ACCESS_TOKEN`/`WHATSAPP_PHONE_NUMBER_ID`. Silently no-ops (resolves immediately) if either is unset, so the webhook's actual job works end-to-end without them — implemented rather than skipped, since a single `fetch()` call was judged not to add meaningful complexity, but its own failure is caught and logged separately from an ingestion failure so a successful ingest with a failed reply doesn't read as a pipeline failure.
- **⚠️ SECURITY, deliberately left as-is per the task**: this endpoint has no way to verify a request actually came from Meta — anyone who discovers the URL can POST an arbitrary payload and have it written to the database through the service-role client (bypasses RLS by design, same as every other ingestion entry point). Acceptable for a hackathon demo; flagged with a comment directly in `route.ts` pointing at Meta's `X-Hub-Signature-256` HMAC verification docs for whenever this needs to be closed. Not implemented now.
- **Can't be exercised against a real Supabase project from this sandbox** — `middleware.ts` needs real `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` to construct its session client on *every* non-static request (not just `/student`/`/admin` — the route-guard logic only applies there, but the client construction that precedes it runs unconditionally), and this sandbox has no real project to point at. This isn't specific to this route; it's the same reason no route in this repo can be smoke-tested end-to-end here. Verification for this pass is `tsc`/`eslint`/`vitest`/`next build` plus a route-collision-free production build — the same bar every other pass in this repo has cleared without a live Supabase project.

## Deterministic engine (clashes & free slots)

`lib/deterministic/` implements clash detection and free-slot matching (docs/requirements-traceability.md Features 2.4/2.5) as plain TypeScript — not a Postgres function or Edge Function, even though `supabase/schema.sql`'s own closing notes mention those; see `docs/data-model.md` §5 for why (no such infrastructure exists in this repo, and `docs/architecture.md`'s MVP line already calls for "In-memory/Node.js deterministic engines"). Same pure-function-plus-thin-DB-wrapper-plus-colocated-tests shape as `lib/ingestion/map-to-announcement.ts`:
- `overlap.ts`, `clashes.ts`, `free-slots.ts` — pure, fully unit-tested (61 tests total across these plus the AI/ingestion tests), no DB access.
- `sync.ts` — the DB-fetching/writing wrappers (`syncClashesForStudent`, `syncFreeSlotsForCancellation`, `matchAnnouncementToOpenFreeSlots`, `matchTimetableEntryToExistingCancellations`). Always called with the service-role client — `clashes`/`free_slots` have no write policy for `authenticated` (§Data model below).
- `types.ts` — the narrow row shapes these functions read; not tied to any generated Supabase DB types (this project doesn't generate any).

**Trigger points** — four, per the exact rules this engine implements:
1. New `cancellation`/`event`/`opportunity` announcement → `lib/ingestion/ingest.ts` calls `syncFreeSlotsForCancellation`/`matchAnnouncementToOpenFreeSlots`. Clash detection deliberately does *not* run here — a brand-new announcement has no engagement rows yet, so it can't produce a class_vs_event/event_vs_event clash the instant it's created.
2. Timetable entry added/edited/deleted → `lib/timetable/actions.ts` (`addTimetableEntry`/`updateTimetableEntry`/`deleteTimetableEntry`) calls `syncClashesForStudent`.
3. Interest/registration status changes → `lib/engagement/actions.ts` (`setAnnouncementStatus`) calls `syncClashesForStudent`.
4. Timetable entry added or edited → `lib/timetable/actions.ts` also calls `matchTimetableEntryToExistingCancellations` — the free-slot-matching direction added in a later pass; see "Free-slot matching only worked in one direction" below.

`syncClashesForStudent` recomputes *all* of one student's clashes from scratch (delete + reinsert) rather than incrementally patching — simpler to keep correct across three independent call sites, and cheap at one-student scale.

**`lib/timetable/actions.ts` and `lib/engagement/actions.ts` both now have real callers** — `app/student/timetable/timetable-screen.tsx` (see §Timetable) and the dashboard/discover-feed Client Components' engagement pills (see §Student Dashboard), respectively. Any future UI touching either `timetable_entries` or `student_announcement_status` should keep calling these directly rather than writing to those tables on its own, or the clash-resync won't fire. Unlike the ingestion pipeline, these write through the RLS-respecting client (`lib/supabase/server.ts`) for the actual table write — students own both tables directly per `supabase/schema.sql` — and only reach for the service-role client for the `clashes` resync step.

**`app/(dev)/clash-test`** is the manual-verification harness for this engine, same temporary/unauthenticated pattern the old `/ingest-test` used (see `app/(dev)/clash-test/actions.ts`'s doc comment for why it bypasses `lib/timetable/actions.ts`/`lib/engagement/actions.ts` rather than reusing them: it works against an arbitrary pasted-in student UUID, not a real signed-in session).

**One assumption this engine had to make that the spec left open:** `timetable_entries.day_of_week` is documented only as "0-6, configurable start day, not hardcoded Mon-Sun" with nothing anywhere actually configuring it. `dayOfWeekFromDate` in `overlap.ts` uses `Date.getUTCDay()`'s own numbering (0=Sunday) as the one unambiguous default available — see that function's doc comment before changing it.

**Confirmed bug, fixed in a later pass: free-slot matching only worked in one direction.** `syncFreeSlotsForCancellation` (rule 5, first half) correctly checks a *new* cancellation against a student's *existing* timetable entries — that direction always worked. But the reverse never existed: a student adding a *new* timetable entry that matches an *already-existing* cancellation produced no `free_slots` row at all. Real scenario that exposed it: a cancellation for "BEE, Monday 2-3pm" ingested before the student had "BEE" on their timetable — adding the entry afterward silently did nothing.
- **The fix**: `matchTimetableEntryToExistingCancellations` (`lib/deterministic/sync.ts`) — called from `lib/timetable/actions.ts`'s `addTimetableEntry` *and* `updateTimetableEntry` (an edit can change an entry's day/time/course name to newly match a cancellation it didn't before, so this has to re-run on every edit, not just on create; it doesn't need to run on delete, since a deleted entry has nothing left to match). Reuses `findFreeSlotCandidate` from `lib/deterministic/free-slots.ts` exactly as-is, just called once per existing `cancellation` announcement with a single-entry list (the entry just added/edited) instead of once per new cancellation across every entry — no second, independent matching implementation that could drift out of sync with the first.
- **Duplicate-insert guard**: `free_slots` has no unique constraint on `(timetable_entry_id, cancellation_announcement_id)`, so a repeatedly-edited entry that keeps matching the same cancellation could otherwise pile up duplicate rows on every edit. `matchTimetableEntryToExistingCancellations` reads that entry's existing `free_slots` rows first and skips any cancellation it's already matched.
- **Deliberately narrower than the forward direction in one respect**: it does not also re-run "check existing event/opportunity announcements against the newly freed slot" (rule 5's second half, which `syncFreeSlotsForCancellation` does inline). A slot created this way still gets picked up the moment any *future* event/opportunity is created — `matchAnnouncementToOpenFreeSlots` scans every open slot table-wide, not just freshly created ones — so the only edge case this leaves unhandled is an opportunity that already existed *before* this specific slot was created, which is a narrower gap than the one reported and wasn't part of the task.
- **Test**: `lib/deterministic/free-slots.test.ts` gained a permanent test reproducing the exact "BEE, Monday 2-3pm" scenario — calling `findFreeSlotCandidate` in the reverse-trigger shape (one new entry against one already-existing cancellation) and asserting it still matches. No new *matching* logic exists to test in isolation (the fix is purely "call the same pure function from the other side"), so this test's job is to lock in that the reused function's behavior doesn't implicitly depend on which side triggered the check — only day/course/confidence. `matchTimetableEntryToExistingCancellations` itself (the DB-wrapping half) has no test of its own, consistent with `sync.ts`'s other three functions, none of which are unit-tested directly either — this codebase's established convention tests the pure logic in `free-slots.ts`/`clashes.ts`/`overlap.ts`, not the Supabase-calling wrappers around it, since there's no live Supabase project to test against in this sandbox.
- **To re-verify**: delete and re-add the timetable entry, or edit it (even a no-op-looking edit like re-saving the same values) — either path calls `addTimetableEntry`/`updateTimetableEntry`, which now both run this check. Then look at the `free_slots` table directly (or `/student/timetable`'s grid, once loaded fresh — see that section's own "known scope boundary" about badges not live-updating mid-session) for a new row linking the entry to the existing cancellation.

**Investigated: a reported case where marking two overlapping announcements Interested/Registered produced no `clashes` row, even though both were `event`-eligible categories** (a `registered_update` — "Maths Class Rescheduled" — and an `event` — "Synergy Orientation" — same day, overlapping times). Two specific hypotheses were checked and ruled out:
- **Not a bypassed write path.** Both real call sites — `app/student/dashboard/dashboard-client.tsx`'s `handleStatusChange` and `app/student/dont-miss-this/discover-client.tsx`'s own copy of the same pattern — call `lib/engagement/actions.ts`'s `setAnnouncementStatus` directly, which upserts the status *and* calls `syncClashesForStudent` in the same request. A repo-wide grep for `student_announcement_status` turns up no other write path in the real UI (only this one and `app/(dev)/clash-test/actions.ts`'s intentionally-separate dev harness, which bypasses on purpose — see that section above).
- **Not a category exclusion.** `registered_update` has always been in `CLASH_ELIGIBLE_CATEGORIES` alongside `event`/`opportunity` — a `registered_update` vs. `event` pair, both engaged, overlapping times, same `event_date`, was reproduced directly against `detectEventVsEventClashes` (a temporary throwaway test, not committed) and it correctly returns one `confirmed` clash. `lib/deterministic/clashes.test.ts` now has a permanent test for exactly this category pairing (it wasn't covered before — every existing `event_vs_event` test used `category: "event"` on both sides) plus a second test isolating the one thing that *does* legitimately prevent a clash: two announcements whose `event_date` values don't match.
- **Also checked and ruled out**: a race between two near-simultaneous pill clicks on different cards (the per-card `pending` state only disables that one card's pills, so two rapid clicks firing two overlapping requests is plausible) — `syncClashesForStudent`'s delete-then-reinsert-from-a-fresh-read design (see its own doc comment: "trivially correct and idempotent no matter which... call site called it") means whichever of the two calls' sync step runs *last* always reads both already-committed engagement rows and computes the correct final state, regardless of interleaving order. And `formatCapMeta` (`lib/dashboard/format.ts`) never displays a date/time it doesn't actually have — `relativeDay`'s "This Tuesday"/"Next Tuesday" labels are computed fresh from a real, non-null `event_date` every render, not fabricated placeholder text, so a card showing a specific day/time is good evidence that field really is set.
- **Most likely actual explanation, and not a code bug**: `lib/ai/extract.ts`'s `buildSystemPrompt(now)` resolves a relative date like "next Tuesday" against *that request's own* current time — by design, so it never has to guess (see §The one working pipeline above). Two messages describing what a person would call "the same day," pasted into `/student/ingest` in two separate sessions on two different calendar days, can legitimately resolve to two different absolute `event_date` values — and `detectEventVsEventClashes`'s `a.event_date !== b.event_date` check then correctly does *not* clash them, because as stored, they didn't happen on the same day. This is the same category of gotcha the CONTEXT-anchoring fix in §The one working pipeline was originally built to make *possible* (resolving relative dates at all) — it doesn't make two independently-resolved relative dates consistent with each other across sessions, which no single-message extraction call could do.
- **To re-verify cleanly**: paste both notices in *one single* `/student/ingest` submission (concatenated in one raw-text box, exactly the case `lib/ai/extract.ts`'s system prompt rule 10 exists for — "one raw_text payload may contain many forwarded messages... extract one announcement per distinct notice") so both resolve any relative date against the same anchor, or use an explicit absolute date ("Tuesday, September 22") in both to remove the ambiguity entirely. Then mark both Interested/Registered from the dashboard and check the `clashes` table directly — a `class_vs_class`-style manual trace via `/clash-test` isn't needed here since both call sites already correctly trigger `syncClashesForStudent`.

**⚠️ Requires a schema migration that hasn't been applied to the live project yet.** `announcement_sources` and `contradictions` both had RLS enabled with *no* SELECT policy at all — the RLS client always got an empty result from both, silently breaking trace-to-source, the source-count tag, and the contradiction banner. `supabase/schema.sql` now includes the fix (mirroring the existing `announcements`/`messages` "readable by authenticated users" policies — these are metadata on already-public announcements, not private data), but it must actually be run against the live Supabase project:

create policy "announcement_sources readable by authenticated users" on announcement_sources
  for select using (auth.role() = 'authenticated');
create policy "contradictions readable by authenticated users" on contradictions
  for select using (auth.role() = 'authenticated');

### Real priority scoring (urgency × consequence)

`announcements.priority_score` has existed as a generated column (`urgency_score * consequence_weight`, `supabase/schema.sql`) since the original schema, but nothing had ever actually set either input — every score was effectively 0 the whole time, and the URGENT ribbon ran on a soonest-date fallback instead of real prioritization (see the now-superseded note this section replaces above). Fixed in a later pass with `lib/dashboard/priority.ts`:

- **Computed live, at render time, not by a scheduled job.** `supabase/schema.sql`'s own closing notes suggested a cron job to keep `urgency_score` fresh as deadlines approach (feature 2.3, "time-decay re-ranking"). Deliberately not built — a pure function of the announcement's stored date/time fields plus the current moment needs no scheduling infrastructure, and *is* time-decay re-ranking as a side effect: a score computed fresh on every page load is automatically always current, with nothing else needed to keep it that way.
- **`computeUrgencyScore(announcement, now)`** — 0-100, decaying linearly from 100 (due right now) to 0 at `URGENCY_WINDOW_HOURS` out (2 weeks), then flat at 0 beyond that. Prefers `deadline_at`; falls back to `event_date` + `start_time` (defaulting to midnight) when there's no deadline — same UTC-anchoring convention as `lib/deterministic/overlap.ts`'s `dayOfWeekFromDate`. An already-passed date scores 0, not "maximally urgent" — showing URGENT on a deadline that's come and gone isn't helpful, and there's no "archived" lifecycle state built yet (`docs/requirements-traceability.md` names one, unbuilt) to route stale content elsewhere instead. No date at all gets a low, fixed floor (`NO_DATE_URGENCY = 5`) rather than crashing or defaulting to either extreme — real but deliberately below anything with an actual near-term date.
- **`CONSEQUENCE_WEIGHTS`** — a hardcoded per-category lookup table, exactly what `supabase/schema.sql`'s own closing notes called for ("from a hardcoded lookup table keyed by category... not an AI call"). A genuine product judgment call, with the full reasoning in `priority.ts`'s own comment: `deadline`/`registered_update` weighted highest (1.0 — "you're already on the hook for something," whether via an external deadline or your own prior commitment); `cancellation`/`opportunity`/`event` in the middle (0.6 — worth knowing, not consequential; `event` joins this tier for the same "closest semantic cousin to `opportunity`" reasoning `category-meta.ts` already uses elsewhere); `society_link`/`fyi`/`duplicate`/`uncategorized` lowest (0.2 — reference material or noise, `uncategorized` paired with `duplicate` for the same reason `category-meta.ts` already pairs those two visually).
- **`computePriorityScore`** = urgency × weight — the real replacement for the stored (always-0) `priority_score` column, used as the actual source of truth everywhere the dashboard needs a ranking.
- **`sortByPriorityScore`** — the dashboard's real card order now. `app/student/dashboard/page.tsx`'s query dropped its old `.order("priority_score", ...)` clause (meaningless while every row's stored value was 0) in favor of resorting the shaped announcement list in JS with this function immediately after fetching, before computing the URGENT pick or the diff summary.
- **`pickUrgentAnnouncementId`** — same category-eligibility gate as before (a bare FYI or society link still can't get the ribbon no matter its score), but now picks the single highest real `computePriorityScore` result, and only if it clears `URGENT_RIBBON_THRESHOLD` (15) — chosen so a top-tier item more than ~12 days out, or a no-date item at any weight, doesn't clear it alone, but anything within about a week and a half of a real date does.
- **Deliberately NOT written back to `urgency_score`/`consequence_weight`/`priority_score`** — the task's own point on this was optional, and writing a snapshot of a value that's designed to keep decaying with time into a stored column would go stale within hours, reintroducing exactly the staleness problem computing it live was chosen to avoid. Nothing else in the codebase reads any of those three columns for anything (confirmed via a repo-wide grep), so there's no existing consumer that would benefit from the extra write path.
- **Tests**: `lib/dashboard/priority.test.ts` unit-tests `computeUrgencyScore`/`CONSEQUENCE_WEIGHTS`/`computePriorityScore` directly (near-vs-far dates, a passed deadline scoring 0 rather than maximal, a no-date item never dominating a near-term one of any category, `registered_update` outscoring `fyi` at the same distance in time) plus the updated `sortByPriorityScore`/`pickUrgentAnnouncementId` behavior — the old tests that drove these off a manually-set `priority_score` field were rewritten, since that field no longer drives anything.

**Test data to visually confirm this**: submit (via `/student/ingest`) a mix across a few categories and distances — e.g. a `deadline` due tomorrow, a `registered_update` due in 3 days, an `fyi` with no date, and an `opportunity` two weeks out. The near-term `deadline` should get the URGENT ribbon and sort first; the `registered_update` should sort above the `fyi` even if you give them similar dates (higher consequence weight); the dateless `fyi` should sort near the bottom, not float to the top; and the far-off `opportunity` shouldn't outrank anything closer despite being a "real" date.

## "Don't Miss This" discovery feed (/student/dont-miss-this)

Real, data-wired implementation of docs/product-spec.md Area A.1 / Feature 4.3 — limited-seat opportunities and other discovery-worthy announcements, kept visible regardless of the dashboard's urgency scoring so they don't get buried under time-pressured deadlines. **The spec's original screen mapping puts this inside `/student/dashboard` as a lane** (see `docs/requirements-traceability.md` Feature 4.3, `docs/figma-screen-inventory.md` §1.2) — that's superseded the same way the login routes and the `student`/`admin` route-group mistake were: it's built as its own tab/route instead, matching the tab-based navigation (Action plan / Don't miss this / Communities / Timetable) the Student Dashboard pass itself already established.

## Login / role selection (/login)

**`/login` is one consolidated route with internal UI state, not three separate routes.** `docs/product-spec.md`/`docs/figma-screen-inventory.md`/`docs/requirements-traceability.md` describe (and originally this file did too) a `/student/login` and `/admin/login` as their own screens — that's now superseded the same way `docs/architecture.md`'s original route tree was superseded for `student/`/`admin/` (see below): those docs are still right about the *content* of each state, just not about it being a separate URL. `app/(auth)/login/login-screen.tsx` is a client-side state machine over three states, all rendered from the one `/login` page:

- **`role`** (default, landing state for an unauthenticated visitor) — `role-select.tsx`: two large tappable tiles, "I'm a student" / "I'm an admin".
- **`student`** — `student-auth-form.tsx`: login is the default view within this state; a toggle link switches to a signup form (`full_name`, `class_name`, email, password). Signup calls `supabase.auth.signUp()` passing `role: 'student'`, `full_name`, `class_name` as `options.data` metadata — `handle_new_user()` in `supabase/schema.sql` reads exactly those three keys and creates the `profiles` row itself; this form never inserts into `profiles` directly. If the Supabase project has email confirmation turned on, `signUp()` returns no session and the form shows a "check your email" message instead of redirecting — there was no way to know from this sandbox whether confirmation is on for the live project, so both paths are handled.
- **`admin`** — `admin-auth-form.tsx`: login only, no signup UI, since an admin's scope is assigned, never self-selected (accounts are provisioned manually — see `scripts/create-test-admin.mjs` below, and `scripts/create-test-admin-society.mjs` for the society-scoped counterpart added in the Admin Dashboard pass). After a successful `signInWithPassword()`, it calls the `checkAdminAccess()` Server Action (`check-admin-access.ts`), which re-checks `profiles.role === 'admin'` (via the RLS client) and looks up a matching `admin_scopes` row via the service-role client. `admin_scopes` now has a real SELECT policy (`admin_scopes` has RLS enabled but no policy yet was the state through the login pass; see §Admin Dashboard below for the policy this file now has and the still-pending live migration) — `check-admin-access.ts` was left calling the service-role client rather than switched over, since bypassing RLS here is still correct either way and touching working, already-shipped code wasn't part of the task that added the policy. No match on either check → the form signs the session back out and shows an "Access Restricted" sub-state in place of redirecting, rather than leaving the visitor silently authenticated on the login screen.

All three states share `components/canvas-background.tsx` (the gradient/floating-symbol backdrop) and the `components/ui/` primitives (`PinCard`, `Button`, `TextField`) — pulled out of the Student Dashboard pass specifically so this screen wouldn't duplicate its visual language; see `components/icons.tsx` for the same move applied to the base icon set (dashboard's own `app/student/dashboard/icons.tsx` now only holds the dashboard-specific `CategoryIcon` mapping). The dashboard's own `Card` component was deliberately *not* generalized onto `PinCard` — its category-driven, animated, multi-state behavior is real complexity specific to that screen, and the login tiles/form container don't need any of it.

Validation uses `zod` (already a dependency, see `lib/ai/extraction-schema.ts`) rather than a new form library — plain controlled inputs plus the schemas in `app/(auth)/login/validation.ts`. Auth calls go through the browser client (`lib/supabase/client.ts`) only; nothing in `app/(auth)/login/` touches the server or admin client except `check-admin-access.ts`'s Server Action.

**`admin_scopes` RLS gap, closed.** The table had RLS enabled with no SELECT policy at all since the login pass first flagged it (`check-admin-access.ts`'s own doc comment) — nothing needed to read it through the RLS-respecting client until this page did. `supabase/schema.sql` now has:
```sql
create policy "admin reads own scope" on admin_scopes
  for select using (auth.uid() = profile_id);
```
scoped to the querying admin's own row only, same "own row" shape as `"read own profile"`/`"student manages own timetable"`. **⚠️ Requires a migration against the live Supabase project** — this is a fresh policy add (no existing policy to drop first), same shape as the `announcement_sources`/`contradictions` addition in §Student Dashboard: run the `create policy` statement above directly against the live project. Until it runs, `/admin/dashboard`'s scope lookup comes back empty for every admin and the page falls through to its defensive "no assigned scope" error state (see below) even for a correctly-provisioned admin.

**Page structure** (`app/admin/dashboard/page.tsx`, a Server Component) — looks up the signed-in admin's `admin_scopes` row through the RLS client (now that the policy above exists), plus the `societies.name` for a society scope (`societies` has no RLS enabled at all — absent from `supabase/schema.sql`'s `alter table ... enable row level security` list entirely, so a plain `select` needs no special client). Three outcomes, all rendered from the one page via `admin-dashboard-screen.tsx`:
- `scope_type = 'class'` → the CR form (`class-update-form.tsx`).
- `scope_type = 'society'` → the Society form (`society-update-form.tsx`).
- No scope row at all → a defensive error card, not a crash — matches the task's own explicit ask, and is also the actual behavior every admin will see until the RLS migration above is run.

**Submission logic — deliberately skips the Gemini pipeline.** Per the task and docs/product-spec.md's own framing of admin submissions as Tier 1 ("Verified Admin Submission") in the Source Trust Hierarchy (docs/requirements-traceability.md Area C §2), this is already clean, structured input — `lib/admin/actions.ts`'s `submitClassUpdate`/`submitSocietyUpdate` build `messages`/`announcements`/`announcement_sources` rows directly, no `lib/ai/extract.ts` call at all. `confidence` is always `'clear'`; `why_it_matters`/`what_to_do_next` are left `null` (both nullable columns) rather than fabricated, since the task's own field list for these two forms doesn't collect narrative text — a card with neither just renders without those lines (`card.tsx` already handles this: both are conditionally rendered). `messages.raw_text` is a plain serialization of the structured fields (e.g. `"Class: CSE-2028-A\nSection: B\nCourse: Database Systems\nStatus: Cancelled\n..."`), built by the pure, unit-tested `buildClassUpdateDraft`/`buildSocietyUpdateDraft` (`lib/admin/build-submission.ts`) — not free text the admin typed, but real enough to give trace-to-source something to show, matching the task's own instruction.

Both Server Actions write through the service-role client (`createAdminClient()`), same as `lib/ingestion/ingest.ts` — `messages` and `announcement_sources` have no INSERT policy for `authenticated` at all regardless of role (see §Data model below), so there's no RLS-client path available for those two even though `announcements` does have an `"admins insert within scope"` policy (its own comment notes the scope-match itself is enforced at the app level, not in SQL) — using the admin client uniformly for all three inserts avoids depending on that policy's partial guarantee. **The admin's own `class_name`/`society_id` is always re-looked-up server-side from `admin_scopes` keyed by `auth.uid()`, never trusted from the client** — the pre-filled/locked Class or Society field in each form is display-only; a CR literally cannot submit for a class other than the one their own scope row names, matching the doc's scoping rule.

**`submitClassUpdate`'s `messages` insert also sets `submitted_by_class_name: scope.class_name`** — added in a later pass (see §Cross-student data isolation's "Follow-up fix" below) once that field became the `announcements` SELECT policy's real class-matching key. Without it, a CR's own `cancellation` submission would have silently become invisible to their own class — `cancellation` isn't one of the four cross-class categories, so it depends on this match the same way a pasted class-specific message does. `submitSocietyUpdate` doesn't set it: `event` is already cross-class, so it was never gated on this field.

**Deterministic-engine parity with the AI pipeline.** A CR's `cancellation` submission calls `syncFreeSlotsForCancellation` right after insert, and a Society Coordinator's `event` submission calls `matchAnnouncementToOpenFreeSlots` — the exact same two trigger points `lib/ingestion/ingest.ts` already uses for those categories (see §Deterministic engine below). Skipping these would have silently made admin-submitted cancellations invisible to free-slot matching and "Don't Miss This" spotlight-style matching, even though nothing about the task called this out explicitly — it follows directly from treating admin submissions as first-class `announcements` rows, not a lesser path.

**Link verification is intentionally NOT run through `verifyLink`** (`lib/ingestion/verify-link.ts`) for a Society submission's registration link — `link_verified` is set to `true` whenever a link is present. `verifyLink`'s domain-allowlist check exists to catch a spoofed domain in *untrusted pasted text* (see §Link verification below); an authenticated, manually-provisioned, scope-checked admin typing their own registration link is exactly the trust case that check is an approximation of in the first place, not a case it needs to re-derive.

**Fields collected, and why they're narrower than `docs/product-spec.md`'s original Area B.2/B.3 lists**: no Course Code, Teacher Name, or Venue/Room field on either form — `announcements` has no matching column for any of the three (see `docs/ai-contracts.md` §3's own removed-fields list for the AI schema; the same columns-that-don't-exist constraint applies here). CR form: Class (locked from scope), Section, Course (→ `linked_class_name`, `match_confidence: 1` — an admin-typed course name is the highest-confidence version of the same text match the AI pipeline does with its own, lower `match_confidence`), Status (`Cancelled`/`Rescheduled`/`Room shift`/`Urgent announcement` — always inserts as `category: 'cancellation'` regardless of which status is picked; there's no separate enum value per status, so the distinction only lives in the title/status label, not in `category`), Date, optional Start/End time. **Real bug found in testing, fixed in a later pass: field labels on both forms were nearly invisible.** `components/ui/text-field.tsx`'s shared `TextField` colors its label `var(--forest)` (a dark green) by design — that's correct on the light mint card every other caller (`/login`, `/student/timetable`'s form) renders it inside, but these two forms sit in a plain, near-transparent `.card` directly on the dark page background, not a mint card, so the same dark-green text was almost unreadable against it. Fixed with a scoped override, not a change to the shared default (which is still correct everywhere else it's used): `TextField` gained an optional `labelClassName` prop (every other call site omits it and renders identically to before), and every `TextField` in `class-update-form.tsx`/`society-update-form.tsx` now passes `labelClassName={styles.fieldLabel}`, a new rule in `admin-dashboard.module.css` setting `color: var(--muted)` — the same `#9dc2a2` value already used for label/secondary text directly on this dark canvas elsewhere (the tab row's `.tab` in `app/student/shell.module.css`, the timetable grid's `.dayEmpty` in `app/student/timetable/timetable.module.css`), not a new color invented for this fix.

`components/` (new as of the login pass) holds cross-screen UI: `icons.tsx` (base SVG shapes + `LogoMark`, `CategoryIcon` stays in `app/student/dashboard/icons.tsx` since it's dashboard-specific), `canvas-background.tsx` (the gradient/floating-symbol backdrop, `.site`/`.bgSym` moved here from `app/student/dashboard/dashboard.module.css`), `ui.module.css` + `ui/pin-card.tsx`/`ui/button.tsx`/`ui/text-field.tsx` (the generic card/button/field shapes both `/login` and the dashboard's chrome are built from).

**`student/` and `admin/` are real path segments, not `(student)`/`(admin)` route groups.** `docs/architecture.md`'s original route-tree diagram wrote them as groups, but a parenthesized segment is stripped from the URL — `(student)/dashboard/page.tsx` and `(admin)/dashboard/page.tsx` both resolved to `/dashboard` and collided (caught by `next build`, not `tsc`). They need to be real folders both because the URLs must actually start with `/student`/`/admin` (that's what `middleware.ts` pattern-matches on) and because the dashboards need distinct URLs from each other. `(auth)`, `(public)`, and `(dev)` are legitimately route groups — those are cases where the group name should *not* appear in the URL.

**`middleware.ts` (at the repo root) has all of its Supabase-session/role-check logic inlined directly in the file — there is no `lib/supabase/middleware.ts` anymore.** It refreshes the Supabase session on every request and enforces role separation from `profiles.role`: unauthenticated → redirect to `/login`; wrong role on `/student/*` or `/admin/*` → HTTP 403. `/login` needs no exclusion from that check — it lives under `(auth)`, a route group, so its URL is just `/login` and was never matched by the `/student`/`/admin` prefix check in the first place.

**Why it's inlined instead of imported from `lib/`:** this logic used to live in `lib/supabase/middleware.ts`, imported by `middleware.ts`. That broke Vercel's production deploy twice in a row, two different ways, neither reproducible by `next build && next start` locally: first with the `@/*` alias (`Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/lib'` — Next's middleware bundle runs in a more restrictive runtime that doesn't rewrite tsconfig path aliases), then again after switching to a relative import (`Cannot find module '/var/task/lib/supabase/middleware' ... Did you mean "./lib/supabase/middleware.js"?` — Vercel's middleware packaging wanted an explicit `.js` extension that neither `next build && next start` nor plain `tsc` ever complained about). Two failures from the same root cause (an external import inside `middleware.ts`'s own bundle, behaving differently under Vercel's specific middleware packaging than any local build reproduces) was reason enough to stop patching symptoms: the logic is now inlined directly into `middleware.ts`, so there's no external import left in its module graph for that bundling step to get wrong. `lib/supabase/middleware.ts` had no other importers (confirmed via a repo-wide grep before deleting it) — if this logic is ever needed elsewhere, re-extract it then, but don't reintroduce a `middleware.ts` → `lib/*` import without re-testing an actual Vercel deploy, not just a local build.

**`middleware.ts` runs on Next's default Edge runtime — nothing in this repo sets `runtime: 'nodejs'`.** After a third `ERR_MODULE_NOT_FOUND` variant on Vercel (`next/server` itself reported unresolvable), the working theory was that middleware had somehow ended up on the Node.js runtime (which Next 15.2+ supports opting into via `export const config = { runtime: 'nodejs' }` inside `middleware.ts`) because `@supabase/ssr`'s `createServerClient` needs Node APIs Edge doesn't have. Investigated and that's false on every count: a repo-wide grep for `runtime`/`'nodejs'`/`'edge'` finds no such config anywhere; `next.config.mjs` has no middleware/runtime-related setting (just `reactStrictMode: true`); there's no `vercel.json` or `.vercelignore`; `.next/server/middleware-manifest.json` lists the middleware entry under `"middleware"` with `server/edge-runtime-webpack.js` as one of its files (Next's Edge-specific webpack runtime) and an *empty* `"functions": {}` map (where Node.js Middleware entries would be registered if that feature were in use) — conclusive proof it's actually building for Edge. `@supabase/ssr` itself is also fine on Edge: its compiled `dist/main/*.js` has only static `require()`s of its own submodules, `@supabase/supabase-js`, and the tiny `cookie` package — no dynamic `require()`, no `fs`/`net`/`crypto`/`__dirname` — it's explicitly designed by Supabase to run inside Next.js Edge middleware, which is exactly the officially-documented pattern this file already uses.

Given that, a `next/server`-unresolvable error is not something a source change in this repo can cause or fix — it's Next's own most fundamental middleware import, provided by the framework/Vercel integration itself, not user code. If this specific error recurs, it points at something on Vercel's project-configuration side rather than another code bug: a stale build cache (try "Redeploy" → "Clear Build Cache and Deploy"), the deployed commit SHA not actually matching the latest push, a Root Directory setting that doesn't point at the actual repo root, or a Framework Preset other than "Next.js". None of those are things this codebase's source controls, and none of them reproduce locally — `next build && next start` passing (as it does here) genuinely doesn't rule them out.

Admin accounts are **manually provisioned** — there's no signup flow for the `admin` role; `handle_new_user()` in `supabase/schema.sql` defaults every new signup to `role = 'student'`. `scripts/create-test-admin.mjs` creates one via `supabase.auth.admin.createUser()` (service-role) for local testing.

## Cross-student data isolation (critical fix)

A real bug found in testing with a second real student account: **`announcements` had a blanket "readable by any authenticated user" RLS policy** — a fully global feed across every class, so a student in one class could see another class's cancellation/deadline announcements. `timetable_entries`' own per-student RLS was already correct; this was specifically the shared-announcements table.

- **Fixed in the RLS policy itself, not in application queries** — the task's own question ("which is actually feasible given Postgres RLS capabilities?") had a clear answer: yes, a `USING` clause can contain an arbitrary correlated subquery/`EXISTS` against other tables (the existing `admins insert within scope` policy already did exactly this), so the *ideal* fix — enforced at the database level regardless of what any query code does — was fully achievable. See `supabase/schema.sql`'s new `"announcements readable by own class or shared category"` policy for the exact SQL and reasoning.
- **A student sees an announcement if either**: its category is inherently cross-class (`society_link`, `event`, `opportunity`, `registered_update`), or the message it came from has a `messages.submitted_by_class_name` matching the viewing student's own `profiles.class_name` (compared case/whitespace-insensitively — two independently-set fields matching on exact case would be a near-certain real-world footgun). `deadline`/`cancellation` (the task's own explicit "must not be shared" examples) and the catch-all `fyi`/`duplicate`/`uncategorized` are class-scoped by default. **This originally matched against `messages.source_group_name` instead — corrected in a follow-up pass; see "Follow-up fix" below.**
- **Why `event`/`opportunity`/`registered_update` joined `society_link` as cross-class**, beyond the task's one explicit example (society links, for Communities' own cross-class purpose): they're exactly `lib/deterministic/clashes.ts`'s `CLASH_ELIGIBLE_CATEGORIES` — the categories the deterministic engine already treats as matchable to *any* student's timetable regardless of which class reported them. `lib/deterministic/sync.ts` runs through the service-role client and bypasses RLS to do that matching, so scoping these three by class as well would have silently broken it: a `free_slots.matched_announcement_id` could end up pointing at an announcement from a different class than the student who has the free slot, and the RLS-respecting title lookups in `app/student/dashboard/page.tsx`/`app/student/timetable/page.tsx` would then come back empty for it. This also matches `docs/product-spec.md`'s own problem statement, which frames "rare extracurricular opportunities are missed" as an inherently cross-class concern — the whole reason `/student/dont-miss-this` exists. This is a judgment call, not a literal instruction — if a future task wants events/opportunities strictly class-scoped too, narrowing the `category in (...)` list back down is a one-line change.
- **All three affected pages — `/student/dashboard`, `/student/dont-miss-this`, and `/student/communities` — needed zero application code changes.** All three already read `announcements` exclusively through the RLS-respecting client (`lib/supabase/server.ts`), confirmed by re-reading each `page.tsx`; none use the service-role client for this table. Communities' own query already filters to `category = 'society_link'` (its whole purpose is a cross-class link directory), so it was already effectively "unscoped" in exactly the way it should stay — the new RLS policy doesn't change its behavior at all, just makes that behavior enforced at the DB level instead of incidentally true because of its own filter.
- **`app/(dev)/clash-test/actions.ts`'s `devListRecentAnnouncements` is unaffected** — it reads through the service-role client (bypasses RLS by design, same as every other write path in this dev harness), so it still lists every announcement regardless of class, which is fine for a manual clash-engine verification tool.
- **Known, deliberate scope boundary**: this is exact-string matching (case/whitespace-insensitive) between `messages.submitted_by_class_name` and `profiles.class_name`. Nothing fuzzy-matches "CSE-2028-A" to "CSE 2028 A" or similar near-misses — but as of the follow-up fix below, both sides of that comparison are now the *same* field (`profiles.class_name`, just copied at two different points in time), not two independently free-typed ones, so a near-miss between them can no longer happen from normal use at all; see "Follow-up fix" below.

**⚠️ Requires a migration against the live Supabase project — this is a policy *replacement*, not a fresh policy add.** Postgres has no `create or replace policy`; drop the old one, then create the new one, exactly as `supabase/schema.sql`'s own migration callout (right after the `announcement_sources`/`contradictions` one) spells out in full. Until this runs on the live project, the old global policy stays in effect and the bug remains exactly as reported. **A second, later migration (below) changed which column this policy compares against — if you're setting up a fresh project, only the later migration's SQL needs to run; this one is historical record of the first step.**

### Follow-up fix: separate class-scoping from the free-text group name label

A second real bug, found in further testing after the fix above shipped: matching against `messages.source_group_name` (whatever free text a student typed as a group's display name, e.g. a WhatsApp group literally named "CSE 1A 🔥") against `profiles.class_name` (an official class name, e.g. `CSE-2028-A`) meant a class's own legitimate messages routinely failed to match their own class and became **silently invisible to the very class they were for** — the fix above closed the cross-class leak but introduced this new, opposite-direction failure mode as a side effect, since it relied on a field that was never meant to carry a matchable class name in the first place.

- **The real problem: one column, two incompatible jobs.** `source_group_name` needed to stay a free-text display label (trace-to-source, the communities directory) — that part was never wrong. It also got pressed into service as a security-relevant matching key, which is the part that was wrong: a WhatsApp group's own display name and an official class name are never reliably the same shape of string.
- **The fix: a second, purpose-built column.** `messages.submitted_by_class_name` (nullable text, `supabase/schema.sql`) is populated **server-side only**, copied from the submitting student's own `profiles.class_name` at insert time (`lib/ingestion/ingest.ts`, keyed off the already-in-scope `submitted_by` id) — never typed by a user, never accepted as a client-supplied option. Because it's always sourced from the same `profiles.class_name` column the RLS policy compares it against, there's no format mismatch left to cause either failure mode. `source_group_name` is completely untouched — same free-text field, same display purpose, same UI (the "Source group name" input on `/student/ingest` still exists and means exactly what it always did).
- **Bulk paste / WhatsApp `.txt` upload**: every message in one submitted batch gets the same `submitted_by_class_name` (the one authenticated student who submitted the whole batch), even if the batch text itself mixes content from several different unofficial group chats — correct by design, not a gap: they're all still being vouched for by one real student belonging to one real class.
- **WhatsApp bot webhook**: there's no authenticated student session for an inbound 1:1 WhatsApp forward, so `submitted_by_class_name` stays `null` for every `whatsapp_bot`-sourced message — no id to derive a class from. This is a real, documented limitation, not a bug: a null never matches any student's class, so a bot-forwarded class-specific message is only visible via the four already-shared categories until there's a real phone-number-to-student mapping. `lib/ingestion/ingest.ts`'s lookup handles this automatically (no `submittedBy` option at all from the webhook → the lookup is simply skipped), rather than needing a special case.
- **Admin form submissions were initially assumed unaffected** (a different, already-correct `admin_scopes`-based *insert* policy governs who can write an admin-submitted announcement) **— that assumption turned out to be wrong for the CR flow specifically**, and was caught and fixed in the same pass: the *insert* policy has nothing to do with the *select* policy this fix changes, and a CR's `cancellation` submission (class-scoped, not one of the four cross-class categories) needs `submitted_by_class_name` set just like a pasted message does, or it would have silently become invisible to its own class the same way the original bug manifested. `lib/admin/actions.ts`'s `submitClassUpdate` now sets `submitted_by_class_name: scope.class_name` (the admin's own verified scope, already looked up server-side — not client input either). The Society flow needs no equivalent change: `event` is already one of the four cross-class categories, so its visibility never depended on this field.
- **Existing test data doesn't survive this migration, on purpose.** Every pre-existing `messages` row gets `submitted_by_class_name = null` (there's no way to retroactively recover which real class a past submission's author belonged to) — old class-scoped announcements become invisible to everyone rather than incorrectly visible to everyone, the safe direction to fail in. Treat old test data as retired, not migrated.

**⚠️ Requires a migration against the live Supabase project** — a new column plus another policy replacement. Exact SQL (safe to run regardless of whether the live project is still on the original global policy or already migrated to the `source_group_name`-based one above — see `supabase/schema.sql`'s own "class-scoping / display-label split" migration note for the full `drop policy if exists` pair):
```sql
alter table messages add column submitted_by_class_name text;

drop policy if exists "announcements readable by authenticated users" on announcements;
drop policy if exists "announcements readable by own class or shared category" on announcements;

create policy "announcements readable by own class or shared category" on announcements
  for select using (
    category in ('society_link', 'event', 'opportunity', 'registered_update')
    or exists (
      select 1
      from announcement_sources asrc
      join messages m on m.id = asrc.message_id
      join profiles p on p.id = auth.uid()
      where asrc.announcement_id = announcements.id
        and m.submitted_by_class_name is not null
        and p.class_name is not null
        and lower(trim(m.submitted_by_class_name)) = lower(trim(p.class_name))
    )
  );
```

**Test plan — simpler now, since nothing depends on a typed string matching anything anymore:**
1. Sign up (or confirm you already have) two student accounts with two different `class_name` values — e.g. `CSE-2028-A` and `ECE-2027-B`.
2. Signed in as the `CSE-2028-A` student, submit a class-specific message via `/student/ingest` (the "Source group name" field can be anything at all now — e.g. a WhatsApp-style label like "CSE 1A 🔥" — it no longer affects visibility), e.g. *"Friday's Data Structures class is cancelled."*
3. Signed in as the `ECE-2027-B` student, submit a different class-specific message the same way, e.g. *"Assignment 3 deadline moved to Monday."*
4. Sign in as the `CSE-2028-A` student → `/student/dashboard` and `/student/dont-miss-this` should show their own cancellation, **but not** the ECE deadline. Sign in as the `ECE-2027-B` student → the reverse.
5. Optionally, also submit one message in a shared category (e.g. a `society_link` or a limited-seat `opportunity`) from either account and confirm both students see it on `/student/communities` (or the dashboard, for the opportunity) regardless of class — unaffected by any of this.

## Data & privacy model (Supabase/Postgres)

See `docs/data-model.md` for the full walkthrough; the two things every change needs to respect:
- **`messages` has a SELECT policy but no INSERT policy for `authenticated`** — same for `announcements`' full write path, `clashes`, and `free_slots`. Any code writing to these must go through `lib/supabase/admin.ts` (service-role, bypasses RLS) on the server — never the anon/browser client. `lib/supabase/client.ts` (browser) and `lib/supabase/server.ts` (request-scoped, respects RLS) are for everything a signed-in user should only see/touch as themselves: `timetable_entries`, `student_announcement_status`, `clashes`/`free_slots` reads, `last_seen`, their own `profiles` row — and, as of the Student Dashboard pass, *reading* `announcement_sources`/`contradictions`, both now `select`-able by any `authenticated` user (⚠️ pending a live migration — see §Student Dashboard above).
- **`admin_scopes` now has a real SELECT policy, scoped to the admin's own row** (`admin reads own scope`, added in the Admin Dashboard pass — see §Admin Dashboard above) — ⚠️ pending the same kind of live migration as the two bullets above; until it runs, the RLS client still gets an empty result for every admin. `check-admin-access.ts` still deliberately reads it through the service-role client regardless (see §Login / role selection above for why that wasn't switched over) — new code can use either, but the RLS client is now a real option where it wasn't before this pass.
- **`app/api/whatsapp-webhook`'s `POST` handler is a fourth unauthenticated write path into `messages`/`announcements`** (alongside the historical `/ingest-test`, and now `/student/ingest` for a signed-in student) — but unlike `/student/ingest`, nothing about this one requires a session at all, by design: it's a public webhook. See §WhatsApp webhook above for the accepted, documented security tradeoff (no request-signature verification yet).
- **`announcements`' SELECT policy is class-scoped, not a blanket "any authenticated user"** — see §Cross-student data isolation above for the real bug this fixes, the exact policy, and the migration that still needs to run against the live project.
